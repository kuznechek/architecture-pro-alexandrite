# Выбор и настройка мониторинга в системе

## Мотивация

Ключвые технические проблемы, ведущие к потере прибыли Alexandrite :

- Потеряно несколько крупных B2B контрактов
- Клиенты не получают заказы месяцами в обещанные сроки
- Медленная работа MES
- Потеря заказов в системе

Внедрение мониторинга позволит быстро обнаруживать технические проблемы, локализовывать их и устранять до то, как их заметили клиенты.

Узкие места системы будут наглядны, что позволит обнаржуить потенциальные проблемы.

С мониторингом можно будет лучше спланировать масштабирование, так как наблюдаемость системы - необходимый критерий для лучшего масштабирования.

## Выбор подхода к мониторингу

Мы применяем комбинированную стратегию сбора метрик, основанную на трех методах:

### 1. RED-метод (для API-сервисов)
Применяется к Online-Shop API, CRM API, MES API. А работе API скорость отклика является ключевым показателем.

Фокус на пользовательском опыте в системах типа «запрос-ответ».

#### Ключевые метрики:

- Rate (RPS) — интенсивность нагрузки

- Errors — доля ошибок (HTTP 4xx/5xx)

- Duration — задержки ответов.

### 2. USE-метод (БД, RabbitMQ, серверы)

Позволяет отслеживать их перегрузку через метрики

- Utilization — загрузка (CPU, память, соединения с БД)

- Saturation — насыщение (глубина очередей RabbitMQ)

- Errors — сбои (Dead Letter Queue, ошибочные запросы).

### 4. Бизнес-метрики (сквозная аналитика процессов)

Дополняют технические показатели и отражают состояние заказов

- Распределение заказов по статусам

- Сквозное время прохождения этапов

- Количество lost заказов (с превышением таймаута на статусе)

## Метрики и ярлыки

**Метрики** показывают изменение состояния системы во времени.


**Ярлыки (labels)** позволяют точно определить местоположение события и различить однотипные метрики.

---

### 1. Шина данных (RabbitMQ)

Мониторинг очередей сообщений для контроля целостности событий.

| Метрика | Цель | Ярлыки |
| --- | --- | --- |
| **Dead Letter Queue Count** <br>(кол-во писем без ответа) | Обнаружение потерянных событий (заказы пропадают и не обрабатываются). | `queue`, `routing_key` <br>`consumer`, `producer` |
| **Messages in Flight** <br>(кол-во сообщений в обработке) | Определение перегруженности шины данных. | `queue` <br>`service` |

---

### 2. API-сервисы

#### Online-Shop API

| Метрика | Цель | Ярлыки |
| --- | --- | --- |
| **RPS** (Requests Per Second) | Определение нагрузки (особенно резкие возрастания). | `endpoint`, `http_method` |
| **Response Time (Latency)** | Выявление задержек в ответах. | `endpoint`, `http_method` |
| **HTTP Status Codes** (200 vs 500) | Проверка корректности работы сервиса. | `endpoint`, `http_method` |
| **CPU / Memory Utilisation** | Определение нагрузки на железо, поиск "узких горлышек". | Встроенные (`host`, `service`) |

#### CRM API

| Метрика | Цель | Ярлыки |
| --- | --- | --- |
| **RPS** (Requests Per Second) | Определение нагрузки (особенно резкие возрастания). | `endpoint`, `http_method` |
| **Response Time (Latency)** | Выявление задержек подтверждения заказов. | `endpoint`, `http_method` |
| **HTTP Status Codes** | Проверка корректности сервиса, выявление пропажи подтверждений. | `endpoint`, `http_method` |
| **CPU / Memory Utilisation** | Определение нагрузки на железо. | Встроенные (`host`, `service`) |

#### MES API

| Метрика | Цель | Ярлыки |
| --- | --- | --- |
| **RPS** (Requests Per Second) | Определение нагрузки от операторов. | `endpoint`, `http_method` |
| **Response Time (Latency)** | Выявление проблем с отрисовкой дашбордов. | `endpoint`, `http_method` |
| **CPU / Memory Utilisation** | Определение перегрузки системы (особенно при подсчете стоимости). | Встроенные (`host`, `service`) |

### 5. Пользователи и клиенты

*Общая цель:* Отслеживание общего роста нагрузки на систему и выявление всплесков от конкретного клиента.

| Метрика | Цель | Ярлыки |
| --- | --- | --- |
| **RPS per Client / User** | Выявление перегрузки, исходящей от одного клиента. | `client_id`, `endpoint`, `http_method` |
| **Concurrent Sessions** | Контроль количества одновременных сессий и соблюдения лимитов. | `client_id`, `service` |

### План действий

#### План по развертыванию системы мониторинга

### 1. Развернуть единое хранилище метрик
   - **Цель:** Создать централизованное хранилище для удобного анализа состояния системы и быстрого поиска причин инцидентов.

### 2. Настроить сбор ресурсных метрик (CPU, память)
   - **Цели:**

     a) Определять «узкие места»: понимать, связана проблема с перегрузкой железа или с кодом.

     b) Оценивать потребность в масштабировании инфраструктуры.

### 3. Настроить сбор метрик бизнес-процессов на уровне API
   - **Цели:**

     a) Количественно оценивать нагрузку на систему.

     b) Выявлять ошибки, возникающие в бизнес-процессах.

### 4. Настроить сбор метрик в шине данных (брокере сообщений)
   - **Цель:** Отслеживать, как, в каком объёме и с какой скоростью перемещаются данные между сервисами.

### 5. Разработать и внедрить дашборды для визуализации метрик
   - **По направлениям:**

     a) **Технические метрики** — нагрузка на инфраструктуру (железо).

     b) **Бизнес-метрики** — количество новых заказов, время выполнения заказа.

     c) **Метрики шины данных** — количество очередей в RabbitMQ, ошибки обмена сообщениями.
