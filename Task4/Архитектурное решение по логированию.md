# Архитектурное решение по трейсингу

## Анализ планирования логов

### Аутентификация
- **Операции**:
  - вход/выход клиентов и операторов
  - создание, изменение, удаление пользовательских данных
- **Системы**: Shop API, MES API, CRM API

### Заказы
- **Операции**:
  - факт создания / завершения заказа
  - изменение статусов
- **Системы**: ручки запросов создания заказов (Shop API и др.)

## Уровни и структура логов

### Обязательные поля для всех событий
- `service` – сервис-источник
- `operation` – выполняемая операция
- `level` – уровень логирования
- `timestamp` – временная метка
- `traceID` – идентификатор трассировки (для связывания событий)
- `orderID` – идентификатор заказа

### INFO – события жизненного цикла заказа

| Событие                     | Описание | Источник |         
|-----------------------------|----------|--------- |
| **INITIATED**               | Создание заказа              | Shop API |
| **FILE_UPLOADED**           | Загрузка 3D-модели           | Shop API |
| **SUBMITTED**               | Оформление заказа            | Shop API |
| **PRICE_CALCULATED**        | Расчёт стоимости завершён    | MES API |
| **MANUFACTURING_APPROVED**  | Подтверждение заказа         | CRM API |
| **MANUFACTURING_STARTED**   | Заказ взят в производство    | MES API |
| **MANUFACTURING_COMPLETED** | Заказ выполнен производством | MES API |
| **PACKAGING**               | Заказ упаковывается          | MES API |
| **SHIPPED**                 | Заказ отправлен покупателю   | MES API |
| **CLOSED**                  | Заказ завершён               | CRM API |

### ERROR – критические ошибки
- Фиксация сбоев, требующих вмешательства.
- **Обязательные поля**:
  - `service`, `operation`, `level`, `timestamp`
  - `errorMessage`, `errorType`

### WARN – предупреждения
- Неудачные попытки входа, попытки доступа к данным вне уровня полномочий.
- **Обязательные поля**:
  - `service`, `operation`, `level`, `message`, `timestamp`

## Мотивация внедрения

### Что получит компания
- Переход от реактивного обнаружения проблем (клиент сообщает о потерянном заказе) к проактивному мониторингу.
- Предотвращение потери заказов и прибыли.
- Быстрый разбор выявленных ошибок.
- Поиск аномалий в бизнес-процессах систем.
- Надёжное подтверждение операций (создание, удаление, изменение).

### Ключевые метрики эффективности
- Количество обращений в техподдержку
- Время восстановления после выявления проблем (MTTR)
- Количество заказов с ошибками
- Количество ошибок взаимодействия между системами

### Приоритет внедрения (первая очередь)
1. **Shop API** – начальная точка создания заказа
2. **MES API ↔ RabbitMQ ↔ CRM API** – основные источники ошибок в жизненном цикле заказа

### Архитектура сбора и анализа логов

[jewerly_c4_model+tracing+logs.drawio](https://github.com/kuznechek/architecture-pro-alexandrite/blob/feature/Task4/jewerly_c4_model+tracing+logs.drawio)

- **Cоздать единые поля в структурированных JSON-логах из всех API, централизованное хранение и анализ**
- **Компоненты**:
  - **Filebeat** – агент на стороне сервиса, собирает и отправляет логи
  - **Logstash** – конвейер обработки данных (получение, фильтрация, обогащение)
  - **Elasticsearch** – хранилище и поисковый движок
  - **Kibana** – визуализация и интерфейс анализа

### Политика безопасности
- **Запрет на персональные данные** – в логи не попадают ПДн.
- **Контроль доступа**:
  - Отсутствие публичного доступа (только корпоративная сеть)
  - Ролевая модель: чтение / поддержка (саппорт) / администратор
- **Аудит доступа** – логирование всех операций с данными логов

### Политика хранения
- Раздельные индексы для каждой системы (Shop, MES, CRM)
- Фиксированные сроки хранения логов и событий

## Необходимые мероприятия для превращения системы сбора логов в систему анализа логов

### Выявление критических ошибок (алерты)
- Резкий рост ERROR в MES, Shop, CRM
- Увеличение задержек ответов операций
- Задержка изменения статуса заказа (бизнес-метрика)
- Резкий рост запросов создания заказов (возможная DDoS-атака или «шторм» от партнёра)

### Поиск аномалий
- Резкий рост ошибок от одного продавца (возможна поломка интеграции)

## Критерии выбора технологий

| Технология     | Стоимость                                             | Произв-ть | Масштабируемость                         | Скорость внедрения |
|----------------|-------------------------------------------------------|-----------|---------------------------------------- -|--------------------|
| **ELK**        | Основное бесплатно, расширения платные                | Хорошая   | Горизонтальная, расширения платные       | Средняя            |
| **OpenSearch** | Бесплатно, оплата только ресурсов                     | Хорошая   | Горизонтальная                           | Средняя            |
| **Splunk**     | Оплата по объёму хранимых логов                       | Высокая   | Высокая, платная                         | Низкая             |

Выбор стека зависит от бюджета, требований к производительности и наличия экспертизы в команде. ELK и OpenSearch – наиболее популярные open-source решения, Splunk – мощная, но коммерческая альтернатива.
